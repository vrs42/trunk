What does "Contrived" mean here?
==============

I admit "Contrived" is not the proper exact meaning;  you COULD contrive to show how it coud happen, but that's besides the point.  It's more a matter of if you just let it happen and do not apply proper care, it will tend to just happen.  Not sure the best word, you figure it out.  the relevant point is this:

You can create a situation where there are empty entries with non-empty entries after them.  Only when the last empty entry is emptied, does it bother to zero it out.  There is an internal difference between a true empty and a deleted entry.  There never was written anyway to exploit the difference, but this is what MS-DOS copied from us; the first character is just made impossible; stick an unsupportable value there outside of the limited character set legal in file names such as the code for ?? 77 octal in the first char position.  Then, you could write a utility to show all non-truly-empty entries as they appear, literally ?OOBAR formerly FOOBAR for example.  It still is a place-holder and not valid as a file, but it makes it print as an official <EMPTY> in the printout, etc.

Now, if you are in fact deleting the last active slot [which means the next one is 0000;0000;0000] then make this one 0000;0000;0000 to become the now-current last active directory slot.

Thus, by some form of happenstance order, should the very last file be deleted, thus it becomes truly empty, no attempt is made to look for the previous one as a candidate for becoming the new last one as some might suggest to automagically take care of this circumstance.  Thus, if you delete the last one, a new CAtalog command will show all prior slots, even if they are empty, thus a directory listing could end with a collection of <EMPTY> printout, etc.  Thus, deliberately get rid of each and every one of them this method:

Use the ENter command to get that last one filled; in general this means you also have to fill in any prior ones anywhere, but use names that mean DUMMY to you in our own mind.  Then DElete them in the reverse order they occur in.  That way, each is in turn the last actual one, and thus it gets cleaned up, repeat in reverse order as many times as necessary and you can prevent trailing empty slot printouts, etc.

So, pick some verbiage to make it make sense in light of the explanation.  It happened for whatever reason; the suggestion can be used to cosmetically clean it up, and in the fact being unable to know what was there before while all <EMPTY> entrees in theory can show the trailing file name characters if available, etc.

"... to avoid problems" - What kind of problems?  Would this create empty entries that cannot be reclaimed/reused?
==============
no, that's never a problem.  But there are situations that can be problematic that can be avoided.

Problems could include complications of fixing up for accidental erasure and not remembering which slot was the one to be repaired;  If all are filled, only one will be empty so the repair should be obvious.

Other issues have to do with contriving the exact position to make it be accessed faster such as ordering in general and the notion of interleaving files logically accessed sequentially but needing the interleave to avoid overhead associated with such as DECtape searching restrictions.  You cannot just search in the same direction for the next block, you have to allow for coasting thus, the next forward-first search can only be allowed for a sufficently forward target next file.  Thus, if you interleave some unrelated files to force the current set being considered to have an interleave, the smart-search tape hanlder will always roll forward through the entire pass through all of them.  If they are physically adjacent, it must do a reverse-first search and turn around by nature.  Fortunately, the length of a single TFS file is a bit longer than the coast factor, thus guaranteeing the all forward searches will be successful and avoid intermediate turn arounds, etc.

The goal is to have the terminal look like aligned to every 8 spaces.  TA noarg outputs just the <Ht> character hoping the terminal just does it right.

TA 3 simulates that with the correct mumber of spaces to force alignment; no actual HT character is outputted.

TA 5 is the same as TAb no arg except padded for the model 35 with calculated idle character counts; this is much faster than tab 3, but only for the 35.  Most hardware like it today, but the extra idle characters slow it down if not necessary on other than 35 hardware.

TA 0 is for ugly but fast printing.

If the carriage has to move only 1 or 2 characters, no need for any IDLE characters.  If it needs to move 6 or 7 positions, there better be two idle characters after the <HT> is sent to allow it to physically move over and then stabilize before any further printing.  all other cases output exactly one extra idle character afterwards, etc.

 5) During command entry, typing control-R or control-T is generally allowed.
    Control-R rewinds the current system tape unit.  Control-T rewinds and unloads
    the current system tape unit.

    Actual tape operations are hardware-dependent; either or both commands may not
    be supported on any specific system.  On the TC01/TC08 DECtape system, control-R
    rewinds the current system tape; control is immediately returned to the keyboard
    monitor; the DECtape controller will stop the tape in the reverse end zone.
    Control-T on the same DECtape hardware will rewind the tape, then force the tape
    off the reel to fully unload it.  If the drive is a TU56, the tape will spin
    freely until stopped by the user.  On a TU55 drive, the drive brakes will lock
    thus stopping the tape.  Control is transferred back to the keyboard monitor
    after all tape operations have completed.

    Control-R and Control-T are not available during BATCH operations.
