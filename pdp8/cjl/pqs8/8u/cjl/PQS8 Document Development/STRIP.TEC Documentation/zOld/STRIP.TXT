Technical level: Intermediate+.  Some working knowledge of TECO required; access to
a TECOC reference document is highly recommended to fully understand some of the
more arcane TECO commands used.  (Note: Advanced TECO users may use a larger subset
of TECOC in their manual editing work; however, some of the commands documented here
will exceed even their working knowledge of TECO as well; certain commands are
hardly ever used outside of TECO macros; some are virtually exclusive to TECOC.)

Introduction.

Various components of the P?S Extended PDP-8 Simulator (PEPS) package (an extension
to the SIMH PDP-8 simulator for Windows) use the STRIP.TEC macro file to filter and
correct various file quirks in output files created within the SIMH simulated PDP-8
environment.  These aberrations are usually caused by minor programming errors that
went virtually unnoticed when originally used on then-present day hardware.  This is
because physical lineprinters and similar output devices generally could tolerate
modest formatting errors (and many programmers were complacent).

Prior to the use of simulators, printer users were willing to tear off output
perhaps after manually separating pages (or at least removing extraneous pages on
either side of the listing).  Few programmers cared about minor anomalies; merely
obtaining a listing was often a luxury.  (Note: Some users were especially picky
regarding the way fan-folded listings were folded, preferring a top page with the
fold at the bottom; as necessary, this could include an additional blank page after
the last printed page with the fold at the top.  Failing to obtain this precise
result led to manually refolding the pages; repeat printing the listing merely to
obtain the desired result was considered prohibitive.  Savvy users learned the
behavior of specific lineprinters to generally assure the final result would be
obtained without resorting to refolding; however, if the only "problem" was the
"wrong" fold direction, listings were generally refolded while waiting for the next
file to print; access to lineprinters was typically so limited that elaborate
scenarios were planned to obtain printed output sometimes from relatively remote
computer installations.)

Processing output files.

Today we expect to either read the lineprinter-oriented output directly in an editor
such as Windows Notepad, or perhaps publish the output through a word-processor or a
.PDF file creator.  As such, all minor aberrations must first be removed for the
benefit of these "modern" facilities, which tend to easily reveal such quirks (which
are often dealt with in a heavy-handed manner).  (Generally, fan-fold paper is no
longer used, but may be simulated using available utilities.)

The burden of printing has shifted to post-processing within the host environment
(in this instance Windows or perhaps MS-DOS) which can be somewhat "hostile" to the
raw output created by prevailing programs such as OS/8 PAL8 and P?S/8 PAL.  In
certain cases, the output can be tainted by the deliberate insertion of
inappropriate characters as part of an ill-conceived design (which was demanded by
programming managers with a twisted agenda).  The reasoning behind all of the
problems dealt with here is beyond the scope of this document; the only concern is
how STRIP.TEC resolves them.

The PEPS Package enhancements allow easy review of the simulated paper-tape and
lineprinter output files.  For those interested in viewing specific quirks, the
files can be displayed before and after STRIP.TEC is applied.  (Note: Viewing
OS/8-generated text files before filtering may prove difficult; the files are
usually created with mark parity set on every character.  Editors are available
such as EditPad Lite, which can interpret text encoding as seven-bit ASCII using
nonstandard settings.)

TECO macro arguments and execution.

The TECO macro STRIP.TEC is launched by the following command inside of the batch
files which are initiated by the shortcuts (Commands) section of the package:

TECOC MUNG STRIP.TEC,%PTO%

The PTO environment variable contents are derived from the %1 argument as passed to
the relevant batch files.  By specifying an independent variable, flexibility in
command formation is achieved and readability is enhanced.  Generally the contents
of PTO will be the complete pathname of the file to be processed.

The MUNG sub-command places the entire contents of STRIP.TEC into an internal buffer
within TECOC.  (Note: Various implementations of TECO have equivalent startup
mechanisms which may not be compatible with TECOC.  The differences, although
generally minor, must be dealt with as required.  STRIP.TEC is designed to work with
TECOC only; minor changes may be necessary to use STRIP.TEC with other TECO
programs.)  As used here, the contents of the PTO variable are placed into the edit
buffer; STRIP.TEC execution commences as the contents of an internal buffer
(equivalent to an internal unnamed Q-register).  (Note: Startup conventions and
exact mechanisms used to pass command-line arguments to TECO are extremely
implementation-specific.  In some versions, the string is passed as the text within
a Q-register perhaps different from another Q-register within which are the macro
contents; see specific TECO release documentation for more information regarding
startup and initial argument passing considerations.)
 
Note: Except where otherwise indicated, $ refers to the escape character (<ESC>)
(ASCII code 27 decimal, 32 octal), which has no defined printing character; when
viewing a macro within most versions of TECO, "$" characters are displayed as a
substitution for the escape character; this includes displaying escape characters
within the edit buffer using any of the usual viewing commands.  This is why it is
difficult to edit a TECO macro other than within TECO itself.  The escape character
is used as a terminator of a string or command in most instances; a macro must
contain escape characters by nature.  The situation is often complicated as TECO
macros are known to dynamically create other TECO macros to be executed from the
TECO macro program.  As such, these created TECO macros will also contain escape
characters.

The § character is used to show a continuation of a long line within this document.
(Note: The actual line contents does not include the § character.)

Fortunately, TECO allows direct insertion of individual characters by character
code.  The sequence 27I$ is often used for the purpose of inserting <ESC>
characters.  (Note: Some programmers are more comfortable with octal values; by
executing the Control-O command, all further numeric input will be evaluated in
octal radix until a Control-D command is executed to return the input radix to
decimal.  In that context, the sequence 32I$ is often used to achieve the same
result.  Future releases of STRIP.TEC may use octal radix notation given the number
of special case character codes processed.)

Similarity of different commands.

The Insert (I) command, when passed a numerical argument (and terminated by an
escape character), creates a single character in the edit buffer with the code of
the numerical argument.  The numerical form of the "I" command requires a trailing
escape character to distinguish this from the text form of the "I" command which
(potentially) allows multiple insertions of text strings.  (Note: Specifics of the
text form of the "I" command could be version-dependent; STRIP.TEC avoids command
extensions where possible.)  The text form of the "I" command (as typically used
when editing files manually) inserts the entirety of an indefinite text string into
the edit buffer when the string terminator is reached; however, it might be used to
insert one text character (as opposed to a numerically evaluated character).  (Note:
Various TECO commands have an analogous duality of functionality determined by exact
usage.  In some instances, the contents of TECO macros must be carefully studied to
determine the exact form of the command being used.)

The description of the entire STRIP.TEC file follows.  Further below, each section
is explained in detail as to what its purpose is.  Please note that line breaks
(<CR>/<LF>) are meaningless within TECO except when those characters would be part
of a string passed to the textual form of the "I" command.  Thus, within this
document, it is merely a line break added for readability.

Known Limitations.

Due to the way OS/8 creates quirky output with the PTP: handler, it is possible for
trailing <FF> characters to occasionally still be present in the file after
stripping.  If necessary, the file may be stripped again to remove the trailing <FF>
character.

Detailed explanation.

Code Fragment		Description

Line #1:		EZ#128EZ$HXQHKGQ0JIEB$ZJ27I$HXBHKMB

EZ#128EZ$		EZ is a version-dependent internal register of TECOC which
			contains various control functions which can affect overall
			operation.  The value already contained in the EZ register
			is inclusively .OR.ed with the constant 128 then written
			back to the EZ register.  By forcing this specific bit to
			the on state, buffer reads limited by <FF> characters are
			inhibited.  Other TECO implementations could handle this
			situation differently or not at all; the logic of the
			STRIP.TEC macro depends on this operational behavior to
			search for <FF> characters.

HXQ			All of the (wHole (H)) text in the edit buffer is copied (X)
			into Q-register Q.  The referenced text is the passed
			complete pathname argument, which is the expansion of the
			PTO environment variable such as:

			%PDP-8_DRIVE%\PDP-8\SIMH\PDP-8\SIMH_Working_Files
			§\PTPFILE.TXT

			which in turn contains the environment variable PDP-8_DRIVE.
			This reduces to something of the form:

			J:\PDP-8\SIMH\PDP-8\SIMH_Working_Files\PTPFILE.TXT

			which is placed in the edit buffer by invoking TECOC in this
			manner.  (Note: The PTO environment variable is generally
			derived from the %1 argument to the batch file initiating
			the TECOC command.  Command-line arguments to invoke TECO
			are extremely system-dependent; this method is valid for the
			MS-DOS and WINDOWS versions of TECOC.)

HK			Kills the entire (wHole (H)) passed edit buffer, since it is
			now saved in Q-register Q.

GQ			Brings the passed string back into the edit buffer.  (Note:
			This method is used to allow additional file commands
			perhaps needed in a future version of the program.)

0JIEB$			Jump to the beginning of the buffer and insert "EB" there.
			The Edit Backup (EB) command, when fully formed, will be
			executed as a TECO macro.
 
ZJ27I$			A trailing escape character is required to complete the
			macro command when it is executed.  The buffer pointer is
			set to point to the end of the edit buffer then an escape
			character is placed into the edit buffer to complete the
			command.

HXB			The entire (wHole (H)) edit buffer contents, which is
			something of the form:

			EBJ:\PDP-8\SIMH\PDP-8\SIMH_Working_Files\PTPFILE.TXT$

			is placed (X) into Q-register B.

HK			Kills the entire (wHole (H)) passed edit buffer, since it is
			now saved in Q-register B.

MB			Q-register B's string contents is executed using a Macro B
			(MB) command.  This sets up the passed file for editing.

Line #2:		Y0J<N^X$;-1A&127U1-D

Y			The Yank (Y) command reads in some portion of the file into
			the edit buffer.  Since <FF> checking is inhibited, only
			overall buffer size determines the exact quantity read in at
			any point.  TECO implementations vary as to exact edit
			buffer size; a number of additional locations are reserved
			in case the edit buffer grows larger.  Typical usage of the
			STRIP.TEC program will generally maintain the overall file
			size; certain specific operations might tend to raise or
			lower the overall size slightly depending on specific file
			contents.  Most character processing consists of merely
			clearing the high-order (mark parity) bit.  As such, the
			overall character count tends to remain constant.

0J			Reset the buffer pointer (J) to the beginning of the edit
			buffer (0).  Most TECO implementations will do this
			automatically after a Yank operation.  TECO programmers
			often include this to clarify the scope of an iteration loop
			that follows.

<			Because of the leading "<" character, what follows up to a
			matching ">" character is executed in an infinite loop;
			various methods exist to break out of the loop, such as a
			failing search operation.  This is the primary operational
			loop for most of the program.

N^X$;			A Nonstop search is performed; all characters processed will
			be forced into the output buffer and (eventually) written
			out.  In this case, the search is a special-case operation:
			the single character Control-X.  This means the search
			argument is any single character of any value.  The only way
			the search can fail returns a special value that can be
			detected by alternate means.  (This situation is not
			searchable in the ordinary sense; it is a status of the
			special condition of the buffer pointer position, not an
			actual character.)

			When any form of search inside of iteration brackets fails
			and a trailing ";" character exists, the normal error abort
			is inhibited; the iteration loop ends and execution
			continues past the ">" character matching the "<" character
			in effect when the failing search was attempted.  (Note: In
			STRIP.TEC there is only one iteration loop; TECO allows
			nesting of iteration loops.)

			Assuming the search succeeded, the buffer pointer is now
			just past the matching character.  Should a character be
			inserted, the buffer pointer will be placed just past the
			newly inserted character.  In some instances the matching
			character will be deleted (causing the buffer pointer to be
			placed just past the previous character, if any).  (Note:
			Character insertion or deletion after a match is only
			performed in certain specific cases.)

			Control-X as used here is the single character Control-X
			(ASCII code 24 decimal, 30 octal); in other contexts, the
			two-character sequence "^" and "X" (or "x") is also allowed.
			However, all search arguments in TECO must be stated
			literally.  (Note: Most TECO implementations echo the
			Control-X character as "^X"; when viewing macros such as
			STRIP.TEC, the correct usage must be confirmed as display
			operations are generally anomalous on this issue.)

-1A&127U1-D		When the "A" command is used with a leading numerical
			argument, the enumerated value is used as an offset from the
			buffer pointer to locate a particular character in the
			buffer.  In this instance the numeric value of the previous
			character (-1) is returned (which is the character that
			matched the search as described above).  This value is then
			masked against the constant 127 (177 octal) via a logical
			.AND. operation which preserves the low-order seven bits
			while removing the high-order bit.  The filtered value is
			then stored (U) in numeric Q-register 1 for further testing;
			the original character (located one position before (-) the
			current buffer pointer value) is then Deleted (D) from the
			edit buffer.  (Later in the program, the test character will
			generally be inserted into the edit buffer unless special
			handling is required.)

Line #3:		Q1-26"NONOTEND$'."EONOCHARS$'0,.P0,.K!NOCHARS!EFEX$

Q1-26"NONOTEND$'	If the test character is not Control-Z (ASCII code 26
			decimal, 32 octal), transfer control (using the gOtO (O)
			command) to the portion of the program labeled !NOTEND!.  If
			the character is Control-Z, execution continues inline to
			finalize the file in the next code section.

			(Note: The host operating system may have different
			conventions regarding the end of file state from the
			operating system that created the file; this is why end of
			file detection is also carried out elsewhere in the program.
			ASCII text files created for/by OS/8 or the P?S/8 SHELL
			generally conform to this convention.  Extraneous characters
			may exist in the file past the Control-Z which are to be
			ignored.  In extremely rare situations, defective OS/8
			utilities may create files that end on the last character of
			the file with an active character; as such, Control-Z might
			not be present.  This situation is handled properly by the
			STRIP.TEC program; however, it may be necessary to remedy
			this situation within OS/8 to add a proper Control-Z
			sentinel character.  MS-DOS and Windows do not support this
			convention internally; exact byte counts are used to account
			proper file length.  P?S/8 conversion programs to/from OS/8
			use safeguards against this problem; OS/8 PIP operating in
			ASCII text mode should be used to correct this problem;
			Kermit-12 for OS/8 implements internal defensive measures to
			prevent this problem.)

."EONOCHARS$'		If the edit buffer pointer is zero, there were no characters
			in the buffer when the Control-Z character was detected.
			This is not a likely situation; however, this is part of the
			"belts and suspenders" approach taken with this program.
			Should this condition apply, transfer control to the portion
			of the program labeled !NOCHARS! bypassing all commands
			beyond this point in the program.

0,.P0,.K		All characters in the edit buffer to this point (0,.) are
			output using the Punch (P) command then deleted using the
			Kill (K) command.  These operations are skipped if the edit
			buffer is empty.  (The label !NOCHARS! follows.)

!NOCHARS!EFEX$		The output file is closed using the End File (EF) command;
			TECO EXits (EX) to the operating system.

Line #4:		!NOTEND!Q1"EOPL8CH1$'Q1-127"EOIGNORE$'OFFCHK$

!NOTEND!		The rest of the program processes the test character
			checking for various special cases.  All additional
                        operations are within the iteration brackets ("<" and ">")
			and will be performed repeatedly.  Each iteration starts
			with the Non-stop search for any existent character until
			failing due to lack of further input.  (Note: All processing
                        for any iteration ends at the label !IGNORE! whether control
                        is transferred there explicitly or execution falls through
                        from the prior command.)

Q1"EOPL8CH1$		If the test character is a <NUL> (ASCII code 0), transfer
			control to the portion of the program labeled !PL8CH1!.
			Files created by OS/8 PAL8 must be checked for a potential
			quirk associated with <NUL> characters near the end of the
			file.  The <NUL> character will be removed; additional
			output filtering may be performed.

			(Note: Surprisingly, many OS/8 text files processed through
			the PTP: handler contain significant quantities of <NUL>
			characters typically in large groups.  Similar special cases
			are known to exist which are handled elsewhere.)

'Q1-127"EOIGNORE$	If the latest character is a <RO> (ASCII code 127 decimal,
			177 octal]), it will be removed by transferring control
			to the portion of the program labeled !IGNORE!; the latest
			character will not be placed into the output file.  Various
			files are known to contain extraneous <RO> characters for a
			variety of reasons.

			(Note: Virtually all P?S/8 device 66 lineprinter output
			starts with a single <RO> character.  This was implemented
			based on misleading information suggesting this as the
			proper technique to initialize the printer interface.
			Future releases of P?S/8 will output a leading <NUL>
			character to enhance compatibility with certain quirky
			printers where a graphic character (such as a heart) is
			printed when <RO> is transmitted.  Proper design will allow
			a one-word patch to restore the historic value of <RO> if
			desired.)

'OFFCHK$		Transfer control to the portion of the program labeled
			!FFCHK! to handle potential <FF> character situations.

!Line #5:		!PL8CH1!0A+1"NOIGNORE$'-7A-12"NOIGNORE$'-7DOIGNORE$

!PL8CH1!		A <NUL> character was detected in the output file.  If this
			is the last character in the file, determine if the file was
			created by PAL8 without the /C (CREF) option set.  In this
			specific instance, PAL8 creates quirky output of several
			blank lines after the last <FF> character with the first
			line incompletely formed.

			This actually represents two different problems: a) The file
			should end with a <FF> character (ignoring trailing <NUL>
			characters which will be removed), b) The blank lines are
			not formed correctly; one consists of merely a <LF>
			character.

			When the /C option is passed to PAL8, a chain to CREF.SV
			will be performed; the final output file will correctly end
			with a <FF> character (ignoring trailing <NUL> characters
			which will be removed).  The blank lines are still present
			in the output file; STRIP.TEC includes programming to
			correct defectively formed blank lines.  This will lead to a
			deliberate blank page in the output consistent with the
			original behavior of PAL8 when used with physical printers.
			(Note: Post-processing of the output file may disallow
			totally blank pages; disposition of blank pages is beyond
			the scope of this program.)

			Since a design goal of STRIP.TEC is to remove the last <FF>
			character, the entire sequence will be removed.  (Note: The
			sequence of characters removed consists of <FF> <LF> <CR>
			<LF> <CR> <LF>; the last character in the file is a <NUL>
			character which will also be removed.)

			Other than this quirky specific case, no rational file
			should be unduly modified.  Another portion of the program
			deals with the exact same problem when <NUL> characters are
			not involved should the file become available in the host
			environment by an exceptional process that avoids the PTP:
			handler artifacts.

0A+1"NOIGNORE$		If the code returned for the next character following (0A)
			the detected <NUL> character is -1, transfer control to the
			portion of the program labeled !IGNORE! to remove the
			latest <NUL> character.  This portion of the program is
			concerned only with a <NUL> character that is at the end of
			the file.

'-7A-12"NOIGNORE$	If the character before the previous five characters is not
			a <FF> (ASCII code 12 decimal, 14 octal), transfer control
			to the portion of the program labeled !IGNORE! to remove the
			last <NUL> character in the file; the file does not have the
			quirky special case present.

'-7DOIGNORE$		Delete the <FF> and all of the other characters through the
			end of the file; transfer control to the portion of the
			program labeled !IGNORE! to continue the iteration loop.
			(Note: The next iteration will break out of the loop when
			the nonstop search fails.)

Line #6:		!FFCHK!Q1-12"NONOTFF$'0A&127-12"EOIGNORE$'QF"NOPASTBEG$

!FFCHK!			This portion of the program checks for <FF> characters.
			This is a pivotal test as anomalies may be present either
			just before or just after a <FF> character.  It is theorized
			most of these problems stem from an incomplete understanding
			of how to properly format logical print pages within various
			programs.  Conforming text files separate pages with a
			single <FF> character; unfortunately, several anomalies may
			be present.

Q1-12"NONOTFF$'		If the test character is not a <FF> (ASCII code 12 decimal,
			14 octal), transfer control to the portion of the program
			labeled !NOTFF!.

0A&127-12"EOIGNORE$'	The test character is a <FF>.  If the next character is a
			<FF> (ASCII code 12 decimal, 14 octal), transfer control to
			the portion of the program labeled !IGNORE! (to ignore the
			test character).  The next iteration will handle the
			situation such that a string of adjacent <FF> characters
			will all be ignored.  Note: The latest character must be
			.AND. 127 (177 octal) since the latest character could have
			the parity bit set.

QF"NOPASTBEG$		Q-register F is tested to determine if this section has been
			executed previously.  If so, transfer control to the portion
			of the program labeled !PASTBEG! to avoid repeat processing.
			(The next section must be used only once.)

Line #7:		'.-11"L0,.DOIGNORE$'!PASTBEG!%F

'.-11"L0,.DOIGNORE$'	Since the <FF> character match is the first one encountered
			in the file, it is possible there are a few characters just
			before the <FF> which is generally the first character in
			the file (assuming it is at the beginning of the file at
			all).  However, certain programs output small groups of test
			characters before the <FF> to ensure the viability of the
			lineprinter interface.  If this is the case, all of these
			characters will be deleted.

			Transfer control to the portion of the program labeled
			!IGNORE! to contine processing; initial <FF> characters are
			removed.

!PASTBEG!%F		Control is transferred to this portion of the program to
			ensure the once-only section is not used again.  Q-register
			F is incremented accordingly.

Line #8:		'.USQH"EOIGNORE$'0A+1"EOIGNORE$'2A+1"NOPL8CH2$


'.US			The current edit buffer position (.) is stored (U) in
			numeric Q-register S.  Certain operations may be performed
			on characters located past the current position; after these
			operations complete, the buffer pointer can be restored
			using the contents of Q-register S that was stored at this
                        earlier point in the program.

QH"EOIGNORE$'		As a special accommodation for output files created by PAL8
			and related OS/8 utilities, if the first character in the
			file is a <FF> character (after first removing all leading
			<NUL> and <RO> characters), it will be removed.  Additional
			<NUL> or <RO> characters may follow; removal is accomplished
			elsewhere in the program.

			Note: When output files from PAL8 and related OS/8 utilities
			are processed by the device 66 LPT: handler, additional
			leading <FF> character(s) may be inserted by the handler.
