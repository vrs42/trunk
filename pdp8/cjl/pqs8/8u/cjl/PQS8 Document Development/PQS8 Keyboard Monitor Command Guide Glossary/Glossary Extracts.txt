1)	For starters, P?S/8 supports teleprinter output overlapping with processing.
	[Non-conforming programs can do it the simplistic way that waits for the
	flag after output, but this slows things down unnecessarily and would
	neeslessly complicate the final implementation of all of these explanation
	"levels" when fully explained, etc.

	This requires an initialization section to make sure it will function, even
	if the program is manually restarted.  [Initialization in this sense means
	even if the program is restarted.  OTHER initialization refers to a one-off
	initialization to interface with the optional P?S/8 components; most system
	programs are not meant to be restarted, thus all initialization is once-only
	code when the program starts, located in some throw-away area such as what
	will be used as some buffer later.  Just about every program has such space
	available "for free".

	If the hardware is used [even if a DECmate] you have to time out the output
	to make sure any previous output has completed.  Typically, P?S/8 loads
	executable programs where the keyboard monitor outputs a character to the
	console and does NOT wait for it.  Thus, by the time a program initialized
	the expected value in the timeout routine is minimal, perhaps only a single
	test pass and no additional wait time.  But this code runs on anything
	including a teletype that takes a whole 1/10th of a second to print that
	character, which is a lot longer than the time to load a program on many
	disk devices, thus there is still some time to wait in that instance.  On
	faster terminals, this could be moot; the code works for all situations.

	Thus, basic initialization is to wait until TSF might skip.  If it does,
	perform TLS with the AC clear to output a <NUL> is the general way to do a
	proper init routine and a non-modified output routine.  [A modified  routine
	would need a flag word to indicate that this is the first time, so don't
	wait.  Best possible in theory, but I have yet to find a device that is
	degraded in any way by output one extraneous <NUL> when starting, thus a
	needless complication in the running output subroutine.  Once-only code
	being "for free" so to speak means the emphasis should always be on the
	overall running code size; longer initialization code is not a factor.]

	If this is running on the DECmate, the rules are different because the
	instruction to test if the flag is up clears the flag!  Thus, minor
	adjustments are made in the output routine.

d)	Core image refers to data stored on blocks of storage where entire pages of
	program or other data are presented in 128 word units meant to be loaded
	into various memory locations as determined elsewhere such as within
	directory or complex file structures that manage loading and mapping issues.

*** "... as determined elsewhere..."?  Would/could that mean "... loaded into
 various memory locations such as within directory or complex file structures that
 manage loading and mapping issues."?  The "as determined elsewhere" makes me think
 there is something like a program deciding where to load the core "128 word units."
  If so, maybe you should specifically state that and state which program(s)
 does/do that? ***

****

No, it is that core-image is what you make of it.  The idea is one or more contiguous
[if there are more than one] are destined to be either loaded into memory or
written from memory to blocks depending on exactly what is going on.  The act of
creating a little piece of an operating system writes core-image binary to 
designated blocks, looking up a file name is reading in the image of the DATA of
a directory that leads to a determination of a block, if it happens to be a
core-image, you are loading it into memory, but not necessarily for execution,
ODT may read in pieces of a core-image to focus on and then write them back, and
various aspects of program execution from ODT, the START command, execution class
command or other places all deal with placing core-image into memory for the
purpose of executing it in place, presumably at a designated starting address.

But it gets worse:  Some core image data is loaded deliberately into the WRONG
memory locations because it cannot yet be put where it must, such as the image of
the slurp loader is read in from a block as core image, but not into 07600-07777
because the system device driver has to perform the work of doing that, so it is
instead loaded into an alternate buffer; later it is MOVED to the intended place
wiping out the system device handler.

Too many pragmatic situations, just better to say it is a versatile concept and
various things have been implemented.  But the most straight-forward is to load
the image of an executable program into the memory locations they were designed to
execute in, start it up, and that defines straight-forward program execution, as
the primary example of where core-image programs instruction and data are used, but
hardly the only one, etc. ****

 3)	Core image [or core-image when used as an adjective].

	Core image refers to data stored on blocks of storage where entire pages of
	program or other data are presented in 128 word units meant to be loaded
	into various memory locations.  Specific loading of groups of core image
	blocks is determined outside of the core image data such as within directory
	or other complex file structures that manage loading and mapping issues.

	Core images stored in order of adjacency by loading address are the most
	efficient form of direct binary storage for executable programs assuming the
	operating system maintains relevant loading parameters [such as the P?S/8
	system program directory].

	P?S/8 system programs are stored in core-image form for at least the first
	load segment of fully adjacent storage blocks; additional segments may be
	defined by the program for additional purposes such as program or data
	overlays.

	Binary files are not core-image files; however, binary files can be loaded
	into memory and saved into system blocks 0020-0057 which is a core image of
	all of field 0.  Once saved, various utilities exist to interact with the
	core image saved in these blocks which are referred to as the system scratch
	area.

	It is possible to save core-image files in P?S/8 by using two separate save
	operations as required.  P?S/8 supports positional files that are each one
	half of this area.  % is the name of the file that is stored in blocks
	0020-0037 and $ is the name of the file that is stored in blocks 0040-0057.
	[Note: These files can be used for a variety of purposes; all usage that is
	incompatible with the core image must be avoided while the current active
	core image is in effect.  The contents of % and $ can be loaded [separately]
	into the tentative file buffer and saved to two named files in the TFS
	directory.  Work on the core image can resume at a later time by restoration
	of the % and $ files.

	A debugging session may be initiated with P?S/8 ODT which will use the
	system scratch area as a virtual image of locations 00000-07577.  [Locations
	07600-07777 are the system kernel and are generally off-limits other than
	certain system parameters that can be used only by fully conforming
	programs.]  All references to extended memory are directly to memory.  The
	user is warned that certain programs will also access extended memory such
	as the P?S/8 PAL assembler.  As such, extended memory loading should be
	considered transient at best.  [Note: The P?S/8 BSAVE utility can save any
	collection of memory locations to a series of binary output files.  The
	storage saved need not be block-oriented or even adjacent; individual memory
	locations can be saved as desired.]  At any time, the core image can again
	be saved or restored using % and $ and two named TFS files as described
	above.

end of e)
